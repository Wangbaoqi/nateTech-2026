## 01. 应用架构模式 (Application Architecture Patterns)

### 1. 目标与进阶阶梯
- **定位**：解决大型中后台与复杂业务系统中代码腐化、职责不清、重构困难等问题。
- **阶段划分**：
  - **阶段一 (基础)**：掌握 MVC / MVP / MVVM 历史演进与数据驱动视图本质；熟悉 Flux/Redux 单向数据流约束。
  - **阶段二 (进阶)**：掌握分层架构思想（UI 层、应用服务层、领域模型层、基础设施层）；深入 Feature-Sliced Design (FSD) 目录规范。
  - **阶段三 (高阶)**：在前端落地领域驱动设计 (DDD) 思想，掌握限界上下文 (Bounded Context)、聚合根 (Aggregate Root)、防腐层 (ACL) 与 CQRS 读写分离。

### 2. 实战工程：`FSD-Clean-ERP` 模块化企业级资产配置平台
- **项目背景**：传统 ERP/CRM 系统因业务庞大容易膨胀为巨石泥潭，修改一处引发全身重构。本工程采用 Clean Architecture + Feature-Sliced Design (FSD) 架构思想规范前端结构。
- **技术栈**：React 19 + TypeScript + Zustand + RxJS + Tailwind CSS + Zod
- **核心模块设计**：
  - `shared/`：UI 组件基底、工具函数、网络请求底层适配器
  - `entities/`：业务实体（如 `Asset` 资产、`Contract` 合同），包含纯粹的数据模型与值对象校验
  - `features/`：用户可操作的独立功能（如 `AssetApproval` 资产审批、`BatchTagging` 批量打标）
  - `widgets/`：组合多个 feature 与 entity 的复合看板区块
  - `pages/`：聚合 widgets 形成的完整页面路由
  - `processes/`：跨页面的复杂长生命周期工作流（如从资产录入到财务结算）
- **分步演进任务**：
  1. **任务 1**：基于 FSD 2.1 规范初始化目录结构，使用 ESLint 边界守卫插件（`eslint-plugin-boundaries`）强制单向依赖规则（底层绝不能依赖上层）。
  2. **任务 2**：实现防腐层 (ACL)。针对后端返回的脏数据结构，在 `infrastructure/acl` 中编写 Mapper 与 Zod Parser，确保领域实体纯净。
  3. **任务 3**：实现 CQRS 模式。复杂报表采用 Query 服务直接拉取只读视图；资产调拨采用 Command 驱动，生成审计事件流 (Event Sourcing 雏形)。
- **验收标准**：
  - 依赖方向严格单向，通过 `npm run lint:arch` 验证 0 循环依赖；
  - 领域业务逻辑 100% 独立于 React 视图生命周期，单测覆盖率 > 90%。

## 02. 页面渲染架构 (Rendering Architecture)

### 1. 目标与进阶阶梯
- **定位**：掌握从传统 CSR 到现代全栈混合渲染的架构选型与调优。
- **阶段划分**：
  - **阶段一 (基础)**：透彻理解 CSR、SSR、SSG、ISR 的生命周期流转、SEO 差异及首屏开销。
  - **阶段二 (进阶)**：掌握 React Server Components (RSC) 原理与 Flight Protocol；熟练运用 Next.js 15 PPR (Partial Prerendering) 动静混合渲染。
  - **阶段三 (高阶)**：掌握 Streaming SSR 边界控制与渐进水合 (Progressive / Selective Hydration)；掌握 Qwik 提出的 Resumability (可恢复性) 与 Astro 岛屿架构。

### 2. 实战工程：`OmniRender-News` 全球多语言资讯与高频行情平台
- **项目背景**：高访问量资讯平台既需要极致的首屏 SEO（静态化优势），又需要金融行情的秒级实时流式更新与个性化推荐。
- **技术栈**：Next.js 15 (App Router) + React 19 + Edge Runtime + Redis
- **核心架构设计**：
  - **静态骨架与通用内容 (SSG/ISR)**：新闻详情主体采用静态生成，基于 `revalidateTag` 实现文章编辑后的增量秒级刷新。
  - **首屏骨架动态混合 (PPR)**：引入 Next.js Partial Prerendering，页面头部导航与静态正文立即可见，无需等待服务端计算。
  - **实时高频行情 (Streaming RSC)**：将股票外汇报价组件包裹在 `<Suspense>` 边界内，利用 HTTP Chunked 流式传输直接输出渲染流。
- **分步演进任务**：
  1. **任务 1**：配置 Next.js 15 PPR 试验特性，构建混合静态外壳与动态流式区域的典型新闻首页。
  2. **任务 2**：抓包分析 React Flight 数据流，编写中间件观察 RSC Payload 序列化体积并实施剥离优化（剔除服务端独有依赖）。
  3. **任务 3**：对比 Qwik/Astro 与 React 19 的水合体积，构建相同的“评论交互区”对比 JS 执行阻塞时长 (TBT)。
- **验收标准**：
  - TTFB < 150ms（通过边缘缓存），LCP < 1.2s；
  - 动态组件水合过程中页面无主线程卡顿（INP < 50ms）。

## 03. 微前端架构 (Micro-Frontend Architecture)

### 1. 目标与进阶阶梯
- **定位**：掌握超大规模组织结构下的前端解耦、多团队自主交付与遗留系统平滑迁移。
- **阶段划分**：
  - **阶段一 (基础)**：掌握 iframe、Single-SPA 核心生命周期（load/mount/unmount）与路由劫持。
  - **阶段二 (进阶)**：深入 qiankun 与 wujie 框架原理；透彻掌握 JS 沙箱（快照沙箱 vs Proxy 沙箱）与 CSS 作用域/Shadow DOM 隔离机制。
  - **阶段三 (高阶)**：掌握基于 Module Federation v2 (Rspack / Webpack) 的运行时联邦，解决跨团队依赖去重、动态版本协商与远程类型共享。

### 2. 实战工程：`FedPortal-MicroX` 企业级微前端协同基座与多业务子应用
- **项目背景**：集团拥有由 React 16 遗留老应用、React 19 新核心系统与 Vue 3 独立团队开发的业务子模块，亟需一个统一步调的底座容器。
- **技术栈**：Rspack + Module Federation v2 + Wujie (Web Components 沙箱) + TypeScript
- **核心架构设计**：
  - **Host 基座应用**：负责 SSO 统一认证、全局路由分发、导航侧边栏、全局 Toast 与基于 BroadcastChannel 的跨应用通信网关。
  - **Remote 1 (Vue 3 报表系统)**：通过 Wujie 运行在 Web Components 隔离沙箱内，规避全局 CSS 样式污染。
  - **Remote 2 (React 19 核心工作台)**：通过 Module Federation v2 接入，共享主应用的 React 核心库与 UI Token 样式体系，达到原生级的秒开性能。
- **分步演进任务**：
  1. **任务 1**：手写一个轻量级 Proxy JS 沙箱，拦截 `window` 属性增删改并在应用卸载时自动 rollback。
  2. **任务 2**：基于 Module Federation v2 配置依赖共享策略（`shared: { react: { singleton: true, eager: false } }`），演示版本错配时的自动回退。
  3. **任务 3**：实现子应用预加载 (Pre-fetch) 策略：当用户鼠标悬停在左侧导航标签时，触发对应 remoteEntry 的无阻塞预解析。
- **验收标准**：
  - 子应用切换无白屏、内存无持续泄漏（切换 50 次后堆内存回落）；
  - 全局样式 100% 隔离，微应用崩溃不影响基座正常运行（集成兜底降级边界）。

## 04. 架构设计原则与决策 (Architecture Design Principles)

### 1. 目标与进阶阶梯
- **定位**：具备架构师思维，用规范化模式、决策模型与弹性机制保障代码长期健壮性与团队一致性。
- **阶段划分**：
  - **阶段一 (基础)**：在前端领域践行 SOLID 原则（如组件单一职责、开闭原则支持插件扩展）。
  - **阶段二 (进阶)**：熟练应用常用设计模式（发布订阅、策略模式、适配器模式、代理模式解耦 SDK）。
  - **阶段三 (高阶)**：掌握架构决策记录 (ADR) 编写、RFC 机制与技术雷达制定；掌握前端高可用弹性设计（熔断降级、重试退避、请求幂等）。

### 2. 实战工程：`Resilient-Payment-SDK` 高可用多渠道前端支付与交易收单内核
- **项目背景**：支付与核心收银台场景下，任何弱网卡顿、支付通道宕机或重复提交都会直接造成财务资损，需要极高的工程容灾与扩展能力。
- **技术栈**：TypeScript (严格模式) + Finite State Machine (XState) + Vitest
- **核心架构设计**：
  - **策略模式 (Strategy Pattern)**：抽象 `PaymentStrategy` 接口，抹平微信支付、支付宝、Stripe、PayPal 的 API 差异。
  - **断路器与自适应退避 (Circuit Breaker & Backoff)**：监测支付通道 API 健康度，当某支付渠道连续超时 3 次触发熔断，自动降级至备用通道。
  - **状态机状态守卫**：使用 XState 刻画支付流程（Idle -> Submitting -> Paying -> Verifying -> Success/Fail），杜绝双击重复付款。
- **分步演进任务**：
  1. **任务 1**：编写 ADR-001 文档（为什么选择策略模式 + 状态机而不是多层 if-else 驱动收银台）。
  2. **任务 2**：手写 `CircuitBreaker` 类，实现 Closed（正常）、Open（熔断）、Half-Open（试探半开）三态转换机制。
  3. **任务 3**：引入防重放 UUID 幂等校验机制与防腐层，实现支付失败自动降级提示策略。
- **验收标准**：
  - 核心状态流转单测覆盖率 100%；
  - 模拟 500 状态码与弱网超时，断路器能在 3 次失败后准确阻断请求并无缝切换备用通道。

## 05. 现代前端工程化体系 (Frontend Engineering System)

### 1. 目标与进阶阶梯
- **定位**：搭建高性能构建管线、Monorepo 架构治理以及规范严密的持续集成部署 (CI/CD)。
- **阶段划分**：
  - **阶段一 (基础)**：掌握 ESM 与 CommonJS 互操作规范；深入理解 Tree Shaking 原理与 `sideEffects` 标记。
  - **阶段二 (进阶)**：精通 Vite / Rollup 插件开发；掌握新一代基于 Rust 的极速构建工具 Rspack 与 Turbopack。
  - **阶段三 (高阶)**：掌握基于 pnpm workspace + Turborepo 的大型 Monorepo 体系，实现增量构建缓存、拓扑任务流水线与自动化发布 (Changesets)。

### 2. 实战工程：`InfraCore-Monorepo` 企业级多包工具链与极速构建体系
- **项目背景**：大型前端团队需要统一维护基础 UI 库、工具函数包、业务核心 SDK 与多个业务应用，面临编译慢、依赖版本割裂、发布混乱的挑战。
- **技术栈**：pnpm + Turborepo + Rspack + Changesets + GitHub Actions + Biome
- **仓库组织结构**：
  - `apps/web`：核心业务应用 (Next.js / Rspack)
  - `apps/docs`：组件库与规范文档 (VitePress)
  - `packages/ui`：企业设计规范组件库 (Tailwind + Radix)
  - `packages/utils`：纯函数算法与通用工具包 (ESM/CJS 双格式导出)
  - `packages/eslint-config`：团队统一的静态代码分析规则
- **分步演进任务**：
  1. **任务 1**：搭建 pnpm Monorepo 依赖拓扑图，配置 `turbo.json` 任务依赖关系，实现远程构建缓存。
  2. **任务 2**：为 `packages/utils` 编写自定义 Rollup/Rspack 构建流程，正确配置 `package.json` 中的 `exports`、`types`，支持自动 Tree-shaking 验证。
  3. **任务 3**：配置 GitHub Actions 工作流：自动化 Lint 门禁、变更包的 Vitest 并行测试、基于 Changesets 的自动语义化版本变更与 npm 预发包发布。
- **验收标准**：
  - 全仓库增量二次构建时间缩短 70%（命中 Turbo 缓存）；
  - 打包产物无残留未使用的 dead code（Bundle 产物分析验证）。

## 06. 极致性能优化工程 (Performance Engineering & CWV)

### 1. 目标与进阶阶梯
- **定位**：基于指标驱动的科学性能优化，彻底攻克 Core Web Vitals 核心瓶颈。
- **阶段划分**：
  - **阶段一 (基础)**：熟练掌握 Performance API、Chrome DevTools Performance 面板录制与火焰图深度剖析。
  - **阶段二 (进阶)**：系统掌握 LCP (最大内容绘制)、INP (交互延迟)、CLS (累积布局偏移) 的成因与优化手段（如 Fetch Priority、Content-visibility、预渲染策略）。
  - **阶段三 (高阶)**：长任务切片与调度（Web Worker 线程分流、`scheduler.yield()` 原语）；虚拟滚动与海量数据渲染（10万+ 节点 60FPS 渲染）。

### 2. 实战工程：`BigData-PerfEngine` 百万级实时行情监控看板与长任务切片调度器
- **项目背景**：金融交易看板同时存在每秒 100+ 条高频 WebSocket 行情推送、复杂图表重绘与大量表格渲染，容易导致浏览器 UI 冻结（INP 飙升至 500ms+）。
- **技术栈**：Vanilla TS / React + Web Workers + OffscreenCanvas + Lighthouse CI
- **核心优化手段**：
  - **计算下沉**：将行情差值计算、排序与复杂聚合下沉至 Web Worker，主线程只接收差量变更。
  - **长任务切片调度**：实现基于 `scheduler.yield()` / `MessageChannel` 的协作式并发调度器，把长达 200ms 的 DOM 重绘任务切分为每个 < 16ms 的微任务。
  - **虚拟化与离屏渲染**：自研双向虚拟滚动网格，结合 `OffscreenCanvas` 进行背景波浪线与折线图渲染。
- **分步演进任务**：
  1. **任务 1**：编写对比 DEMO：复现因循环密集计算造成的页面丢帧与按钮点击无响应，抓取 Trace 火焰图标注长任务。
  2. **任务 2**：封装 `TaskScheduler` 切片执行引擎，将密集计算平滑分散至每帧空闲时间执行。
  3. **任务 3**：接入 `web-vitals` 库捕获真实用户性能（RUM），配置 Lighthouse CI 进行 PR 性能门禁拦截。
- **验收标准**：
  - 10 万行复杂数据滚动无白块、无丢帧（帧率稳定在 58-60 FPS）；
  - INP 指标从 > 400ms 优化至 < 60ms，Lighthouse 性能得分 > 95。

## 07. JavaScript 运行时与 V8 底层 (JavaScript Runtime Internals)

### 1. 目标与进阶阶梯
- **定位**：脱离上层框架语法糖，从 JS 引擎物理层、堆栈内存分配与垃圾回收视角解决棘手疑难杂症。
- **阶段划分**：
  - **阶段一 (基础)**：透彻掌握宏任务、微任务调度细节，Event Loop 与浏览器渲染帧（Render Steps）的准确时序。
  - **阶段二 (进阶)**：深入 V8 垃圾回收（Scavenger 复制算法、Mark-Sweep 标记清除、增量标记与并发 GC）；排查闭包与 DOM 游离泄漏。
  - **阶段三 (高阶)**：深入 Ignition 解释器与 TurboFan 优化编译器原理；掌握 Hidden Class（隐藏类）与 Inline Cache（内联缓存）机制，写出符合 V8 单态（Monomorphic）的代码。

### 2. 实战工程：`V8-MemLeak-Diagnostic` 内存泄漏诊断与对象形态优化实验室
- **项目背景**：长时间运行的单页应用（SPA）或富文本协同文档经常出现“越用越卡”、“标签页崩溃”问题，必须通过工程化手段量化对象内存与优化 V8 编译热度。
- **技术栈**：Node.js (带 `--expose-gc` / `--trace-deopt` 参数) + Chrome DevTools + Benchmark.js
- **实验设计与核心任务**：
  - **实验 1 (内存泄漏复现与定位)**：
    - 构造典型泄漏场景：未清理的全局事件监听器、被意外捕获在长生命周期闭包中的大字符串、脱离文档流但仍被 JS 引用的 Detached DOM 节点。
    - 使用 Heap Snapshot（堆快照）比对，通过 Distance 与 Shallow/Retained Size 定位支配树根节点。
  - **实验 2 (弱引用内存回收治理)**：
    - 使用 ES2021 `WeakRef` 与 `FinalizationRegistry` 实现自动垃圾回收清理缓存器，避免传统 Map 导致的常驻内存积压。
  - **实验 3 (V8 隐藏类与优化去优化验证)**：
    - 编写两组基准测试：一组保持对象属性声明顺序完全一致（单态，共享同一隐藏类 Map）；另一组动态添加属性（多态/超态）。

## 09. 复杂状态管理架构 (State Management Architecture)

### 1. 目标与进阶阶梯
- **定位**：科学划分状态归属，在保证单向可追溯的前提下追求细粒度响应与零多余渲染。
- **阶段划分**：
  - **阶段一 (基础)**：明确状态边界（本地组件状态 vs 全局业务状态 vs 服务端异步缓存 vs URL 参数状态）。
  - **阶段二 (进阶)**：熟练掌握现代状态方案（Zustand 切片模式、Jotai 原子化、Pinia）；深入 Signal 细粒度响应式原理。
  - **阶段三 (高阶)**：精通服务端状态管理（TanStack Query v5）的核心机制：乐观更新 (Optimistic Update)、自动重试、按键失效与离线持久化。

### 2. 实战工程：`Collab-Kanban` 复杂协同看板与离线优先状态引擎
- **项目背景**：类似 Trello / Notion 的多看板拖拽管理系统，包含大量任务卡片移动、标签筛选、网络抖动下的撤销重做（Undo/Redo）与多人实时协同。
- **技术栈**：React 19 + Zustand (切片状态) + TanStack Query v5 + Immer + LocalForage
- **状态设计方案**：
  - **Server State**：所有看板列表与卡片数据交由 TanStack Query 托管，设定 `staleTime: 5000`。
  - **Client UI State**：拖拽过程中的临时位置、选中的卡片浮层使用 Zustand 进行管理。
  - **URL State**：过滤条件、搜索关键字与视图模式强绑定至 URL Query 参数，支持任意链接分享直接还原状态。
- **分步演进任务**：
  1. **任务 1**：实现跨列拖拽的**乐观更新 (Optimistic UI)**。用户释放鼠标后卡片瞬时到位，异步发送变更请求；若后端返回错误，无缝回滚至先前快照并弹窗提示。
  2. **任务 2**：在 Zustand 中实现 Undo/Redo 历史快照环形缓冲区（保存最近 20 步操作）。
  3. **任务 3**：实现离线持久化同步器（Offline Mutation Cache）。断网时操作先存入 IndexedDB，恢复网络后按序自动重放。
- **验收标准**：
  - 拖拽过程页面只触发目标卡片与列的重绘，无全局 Re-render；
  - 断网状态下卡片移动不卡顿，网络恢复后 100% 数据最终一致。

## 11. 前端纵深安全体系 (Frontend Security Architecture)

### 1. 目标与进阶阶梯
- **定位**：构建由内而外的立体化安全防御，杜绝数据泄露、提权攻击与 AI 时代的新型注入风险。
- **阶段划分**：
  - **阶段一 (基础)**：掌握常见 Web 漏洞攻防（Reflected / Stored / DOM-based XSS、CSRF、CORS 预检机制、Clickjacking）。
  - **阶段二 (进阶)**：深入掌握 CSP (Content Security Policy) 配置（nonce-based CSP、`strict-dynamic`）；掌握 SameSite Cookie 与 Subresource Integrity (SRI)。
  - **阶段三 (高阶)**：掌握认证授权高级模式（OAuth 2.0 PKCE 流程、短命 JWT + 静默 Refresh Token）；掌握 AI 原生安全（客户端 Prompt Injection 防御与沙箱隔离）。

### 2. 实战工程：`SecGuard-Vault` 银行级前端安全合规攻防测试舱
- **项目背景**：金融或敏感数据前端系统要求零 XSS 注入可能，即便引用的第三方第三方统计 SDK 被黑，也不允许盗取用户 Cookie 或窃听按键。
- **技术栈**：Next.js / Express + DOMPurify + Web Crypto API + OAuth 2.0 PKCE
- **核心防御模块**：
  - **严格 CSP 标头生成器**：实现基于服务端每次请求生成的动态随机 Nonce，禁止任何 `eval()`、`inline script` 与未授权域名请求。
  - **OAuth 2.0 PKCE 认证客户端**：在纯客户端实现 `code_verifier` 与 `code_challenge` SHA-256 哈希计算，杜绝授权码拦截攻击。
  - **富文本与 Generative UI 隔离沙箱**：集成 DOMPurify 严格白名单过滤，外加 `iframe` 沙箱（`sandbox="allow-scripts"` 严格剔除 `allow-same-origin`）。
- **分步演进任务**：
  1. **任务 1**：编写一组 XSS 攻击 Payload（包含 SVG 脚本、属性反射），在未加防范的页面中演示窃取 LocalStorage；随后部署防御机制完成攻击阻断。
  2. **任务 2**：配置严格 CSP 策略，利用自动化测试工具验证非 Nonce 外部注入脚本被浏览器内核拒绝执行。
  3. **任务 3**：使用 Web Crypto API 实现客户端敏感字段（如银行卡号）提交前通过公钥进行 RSA-OAEP 混合端到端加密。
- **验收标准**：
  - 通过 OWASP ZAP 自动化漏洞扫描工具，0 高危/中危安全告警；
  - 核心敏感 Token 绝不暴露于 LocalStorage，统一采用 HttpOnly + Secure Cookie 存储。

## 13. 可观测性与全面质量工程 (Observability & Quality Engineering)

### 1. 目标与进阶阶梯
- **定位**：实现系统稳定性度量、全链路追踪、异常主动预警以及高覆盖率的自动化测试矩阵。
- **阶段划分**：
  - **阶段一 (基础)**：掌握单元测试与组件测试（Vitest + React Testing Library）；熟练应用 MSW (Mock Service Worker) 进行网络层无感 Mock。
  - **阶段二 (进阶)**：掌握现代端到端测试 (Playwright)，编写鲁棒性高的页面交互流断言；引入视觉回归比对测试。
  - **阶段三 (高阶)**：掌握前端 OpenTelemetry 全链路链路追踪（Trace ID 穿透）；构建 Sentry 错误监控与 RUM 真实用户体验大盘；制定架构守卫规范。

### 2. 实战工程：`SentryTrace-Playwright-Suite` 全链路可观测性与可靠性自动化平台
- **项目背景**：线上偶发报错无法复现、前后端排错互相推诿、每次版本迭代发布心惊胆战。本工程建立从测试门禁到线上监控的闭环防护网。
- **技术栈**：Vitest + RTL + Playwright + MSW + Sentry SDK + OpenTelemetry Web
- **核心架构方案**：
  - **全链路追踪 (Trace ID)**：前端全局网络拦截器生成 `traceparent` Header，贯穿网关、BFF 与微服务，Sentry 报错直接点击跳转至分布式调用链路。
  - **契约测试与 E2E 矩阵**：
    - 使用 MSW 拦截网络，单元测试不依赖任何真实后端服务；
    - 针对登录、加购、结算核心业务流编写 Playwright 跨浏览器自动化用例（支持录制失败操作视频与追踪快照）。
  - **架构守卫 (Arch Lint)**：使用依赖分析工具（如 `dependency-cruiser`）确保业务包不会反向引用宿主包。
- **分步演进任务**：
  1. **任务 1**：编写高可靠性的 MSW 请求契约 Mock 处理器，覆盖成功、服务端 500、网络超时三种边界用例。
  2. **任务 2**：编写 Playwright E2E 测试脚本，模拟弱网丢包与异常输入，验证页面错误边界（Error Boundary）友好展示。
  3. **任务 3**：接入 Sentry 并在错误上报时附带全局上下文（User ID、路由栈、上一步用户操作面包屑 Breadcrumbs），自动关联 Release Source Maps。
- **验收标准**：
  - 核心业务逻辑单元测试代码覆盖率 > 85%；
  - CI 流水线中自动运行 Playwright E2E，遇到线上崩溃能在 1 分钟内通过 Sentry 告警定位到原始 TS 代码行。
