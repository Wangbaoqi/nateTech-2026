# 形式文法与词法分析·ASI - 底层分析

要从根本上理解为什么 JavaScript 解析器会做出看似“奇怪”的决定，我们必须翻阅 ECMAScript 规范中关于形式文法（Formal Grammars）和词法（Lexical）的部分。

## 1. 上下文无关文法 CFG 记号 (Clause 5.1)

ECMAScript 的语法是基于**上下文无关文法 (Context-Free Grammar, CFG)** 来描述的。规范使用了特定的产生式（Productions）记号：

- **终结符 (Terminal Symbol)**: 词法分析的最小单元（如关键字 `if`, `{`, 标识符等）。
- **非终结符 (Nonterminal Symbol)**: 用斜体表示，可以进一步展开为其他终结符或非终结符组合的抽象语法结构（如 *Statement*, *Expression*）。
- **产生式 (Production)**: 规则的定义。左侧是非终结符，由冒号 `::` 或 `:` 分隔，右侧是推导序列。
  - `::` 代表词法文法 (Lexical Grammar) 的产生式。
  - `:` 代表句法文法 (Syntactic Grammar) 的产生式。

**示例**：
```text
IfStatement : 
  if ( Expression ) Statement else Statement
  if ( Expression ) Statement
```

## 2. 4 种 Goal Symbols 详解和切换机制 (Clause 11)

词法分析器（Lexer / Scanner）的职责是将源码字符串切分成一系列有意义的词法单元（Tokens）。
但是，同样的一串字符，在不同的语法上下文中可能有完全不同的含义。引擎通过 **Goal Symbol（目标符号）** 来决定当前使用哪套切词规则。

### 核心 Goal Symbols:
1. **InputElementDiv**: 预期下一个 Token 可以是除号 `/` 时使用。
2. **InputElementRegExp**: 预期下一个 Token 可以是正则表达式字面量（以 `/` 开头）时使用。
3. **InputElementRegExpOrTemplateTail**: 预期可能出现正则或模板字符串尾部时。
4. **InputElementTemplateTail**: 预期解析模板字符串的中间或尾部。

### 解析 `/` 时的底层切换逻辑：
当解析器遇到 `/` 字符：
- 如果前面的语法节点是一个变量或数字（例如 `a`，`1`），解析器当前处于 **InputElementDiv** 状态，`/` 被解析为 `DivPunctuator` (除法操作符)。
- 如果前面的语法节点是一个运算符、括号、或者是语句的开头（例如 `=`, `(`, `typeof`），解析器当前处于 **InputElementRegExp** 状态，`/` 被解析为正则表达式的起始定界符。

## 3. Early Errors 一票否决权机制 (Clause 8)

在很多动态语言中，如果语法有错，执行到那一行才会报错。但 ECMAScript 定义了 **Early Errors** 机制。

引擎在解析完毕生成 AST（抽象语法树），甚至在执行任何一行字节码**之前**，必须先对静态语义 (Static Semantics) 进行验证。一旦违反，立刻抛出 `SyntaxError`，代码一行都不会被执行。

典型的 Early Errors 包含：
- 同一词法作用域内出现重复的 `let`/`const` 声明。
- 严格模式下 `eval` 或 `arguments` 作为变量名。
- `break` 指向了一个不存在的标签。
- `super()` 出现在了非子类构造函数中。

## 4. SourceCharacter 与 LineTerminator (Clause 11)

规范定义，源码是 Unicode 字符流。但在 ASI 和语法换行判断中，只有特定的几个字符被认为是 **LineTerminator (行终止符)**：
- `<LF>`: Line Feed (U+000A) - Unix/Linux/Mac 的换行 `\n`
- `<CR>`: Carriage Return (U+000D) - 老 Mac 的换行 `\r`
- `<LS>`: Line Separator (U+2028)
- `<PS>`: Paragraph Separator (U+2029)

> [!NOTE]
> 诸如 `<SPACE>` 或 `<TAB>` 等空白字符（WhiteSpace）只用于分隔 Token，不会触发任何 ASI 规则，也不会影响文法的受限产生式。

## 5. 核心 ASI 算法 (Clause 12.9) 

规范明确指出：ASI 不是在代码字符串中硬塞字符，而是在产生式解析失败时，**在语法树解析阶段假装存在一个分号**，使文法匹配得以继续。

### 解析算法流程：
当解析器按顺序消耗 Tokens 时，遇到一个不符合当前产生式的违规标记 (Offending Token)：

1. **检查换行**：如果违规标记和上一个合法标记之间存在至少一个 **LineTerminator**，则触发 ASI，假装修补了一个分号。重新评估文法。
2. **检查闭合大括号**：如果违规标记是 `}`，直接在其前面修补一个分号。
3. **检查 EOF**：如果违规标记是因为到达了文件末尾 (End of File)，修补分号。
4. **失败条件**：如果插入分号后变成了空语句 (Empty Statement)，或者成为了 `for` 循环头部的分号之一（如 `for (a \n b)`），则**拒绝插入，立刻抛出 SyntaxError**。

### 受限产生式算法 (Restricted Productions Algorithm)
当解析器匹配到 `ReturnStatement`, `ThrowStatement`, `BreakStatement`, `ContinueStatement` 等规则时：
- 只要跟在对应关键字（如 `return`）后面的第一个 Token 和该关键字之间存在 **LineTerminator**。
- 即使这个 Token 在语法上是合法的（比如是一个花括号 `{` 或一个变量），解析器也**必须立刻在这个关键字后面插入分号**。

这个底层逻辑解释了为什么 `return \n { a: 1 }` 必定会被截断，因为它是规则层面的强制截断，与后续代码是否有违规标记无关。
