# 执行上下文与环境记录 (Execution Context & Environment Record) - 使用维度

## 1. 核心概念与调用栈可视化

在 JavaScript 引擎运行代码时，执行上下文（Execution Context）是评估和执行代码的环境。每次函数调用都会创建一个新的执行上下文并推入调用栈（Call Stack）。

### 1.1 调用栈 (Call Stack)

调用栈是一个 LIFO（后进先出）的数据结构，用于存储代码执行期间创建的所有执行上下文。

> [!NOTE]
> 栈底永远是全局执行上下文（Global Execution Context），栈顶则是当前正在执行的上下文（Running Execution Context）。

#### ASCII 图示嵌套函数调用栈

考虑以下代码：

```javascript
function bar(y) {
  let z = 3;
  return y + z;
}

function foo(x) {
  let y = 2;
  return x + bar(y);
}

function main() {
  let x = 1;
  let result = foo(x);
  console.log(result);
}

main();
```

当执行到 `bar` 函数内部时，调用栈的可视化状态如下：

```text
+-----------------------------------+  <-- 栈顶 (Stack Top)
|  Execution Context: bar           |
|-----------------------------------|
|  LexicalEnvironment: {z: 3}       |
|  VariableEnvironment: {y: 2}      |
|  Code: return y + z               |
+-----------------------------------+
|  Execution Context: foo           |
|-----------------------------------|
|  LexicalEnvironment: {y: 2}       |
|  VariableEnvironment: {x: 1}      |
|  Code: return x + bar(y)          |
+-----------------------------------+
|  Execution Context: main          |
|-----------------------------------|
|  LexicalEnvironment: {x: 1, ...}  |
|  VariableEnvironment: {}          |
|  Code: let result = foo(x)        |
+-----------------------------------+
|  Global Execution Context         |
|-----------------------------------|
|  LexicalEnvironment: {main, foo..}|
|  VariableEnvironment: {}          |
+-----------------------------------+  <-- 栈底 (Stack Bottom)
```

## 2. 执行上下文生命周期：创建阶段 vs 执行阶段

执行上下文的生命周期严格划分为两个主要阶段：**创建阶段（Creation Phase）** 和 **执行阶段（Execution Phase）**。

### 2.1 创建阶段 (Creation Phase)

在引擎执行任何代码之前，会先进入创建阶段。这也被称为“变量提升”（Hoisting）发生的时间点。

1.  **绑定 `this`**：决定 `this` 的指向。
2.  **创建词法环境 (LexicalEnvironment)**：用于存储 `let`、`const` 声明以及函数声明。
3.  **创建变量环境 (VariableEnvironment)**：专门用于存储 `var` 变量声明。

> [!IMPORTANT]
> - `var` 变量在此时被初始化为 `undefined`。
> - 函数声明在此时被完整地存储在内存中（函数提升）。
> - `let` 和 `const` 变量在此阶段被放入词法环境，但**不会被初始化**，处于暂时性死区 (TDZ)。

### 2.2 执行阶段 (Execution Phase)

在此阶段，引擎逐行执行代码。完成变量赋值，并执行具体的函数调用。

```javascript
// --- 阶段演示 ---
console.log(a); // 输出: undefined (var已在创建阶段初始化为undefined)
console.log(b); // ReferenceError: Cannot access 'b' before initialization (let在TDZ)

var a = 10;     // 执行阶段：赋值 a = 10
let b = 20;     // 执行阶段：初始化并赋值 b = 20

foo();          // 正常执行 (函数在创建阶段已完整存入内存)

function foo() {
    console.log('foo executing');
}
```

## 3. var vs let/const 在执行上下文中的差异

在 ECMAScript 规范中，环境记录（Environment Record）分为几种。`var` 与 `let/const` 在上下文中的存储位置和行为有显著差异。

### 3.1 模拟器分析

*   **`var` 声明**：保存在 **VariableEnvironment** 的环境记录中。对于全局上下文，它会成为全局对象（如 `window`）的属性。
*   **`let`/`const` 声明**：保存在 **LexicalEnvironment** 的环境记录中。不会成为全局对象的属性。

```javascript
var myVar = 'varValue';
let myLet = 'letValue';
const myConst = 'constValue';

// 在浏览器环境下：
console.log(window.myVar);   // 'varValue' - var 污染了全局对象
console.log(window.myLet);   // undefined - let 不在全局对象上
console.log(window.myConst); // undefined - const 不在全局对象上
```

> [!TIP]
> 现代工程实践中，强烈建议完全弃用 `var`，统一使用 `let` 和 `const`，以避免变量提升带来的不可预测性以及全局命名空间污染。

## 4. 严格模式 (Strict Mode) 对执行上下文的 3 种影响

严格模式（`"use strict";`）显著改变了执行上下文的行为：

### 影响一：未声明变量的赋值报错

非严格模式下，给未声明的变量赋值会在全局环境中隐式创建一个全局变量。严格模式下直接抛出 ReferenceError。

```javascript
function test() {
    "use strict";
    undeclaredVar = 10; // ReferenceError: undeclaredVar is not defined
}
test();
```

### 影响二：`this` 的默认绑定变为 `undefined`

在非严格模式下，独立函数调用时的 `this` 会默认指向全局对象。严格模式下，`this` 保持为 `undefined`。

```javascript
function checkThis() {
    "use strict";
    console.log(this); 
}
checkThis(); // 输出: undefined
```

### 影响三：禁止删除变量、函数或不可配置属性

```javascript
"use strict";
var x = 1;
delete x; // SyntaxError: Delete of an unqualified identifier in strict mode.

const obj = {};
Object.defineProperty(obj, 'prop', { value: 1, configurable: false });
delete obj.prop; // TypeError: Cannot delete property 'prop' of #<Object>
```

## 5. 多 iframe 中独立 Realm 导致 instanceof 失效

在浏览器中，每个 `<iframe>` 都有自己独立的全局执行上下文和 **Realm**。这意味着每个 iframe 都有自己的内置对象副本（如 `Array`, `Object`, `Error`）。

### 具体展示

当你将一个数组从一个 iframe 传递到另一个 iframe 时，`instanceof` 检查会失败。

```html
<!-- 主页面 main.html -->
<iframe id="myIframe"></iframe>
<script>
  const iframe = document.getElementById('myIframe');
  iframe.onload = function() {
    // 获取 iframe 内部的 Array 构造函数
    const IframeArray = iframe.contentWindow.Array;
    
    // 在 iframe 的 Realm 中创建一个数组
    const arrFromIframe = new IframeArray(1, 2, 3);
    
    // 在主页面的 Realm 中检查
    console.log(arrFromIframe instanceof Array); // false!
    console.log(arrFromIframe instanceof IframeArray); // true
    
    // 工程解决方案：使用 Array.isArray (跨 Realm 安全)
    console.log(Array.isArray(arrFromIframe)); // true
    
    // 另一种跨 Realm 安全的类型检查
    console.log(Object.prototype.toString.call(arrFromIframe) === '[object Array]'); // true
  };
</script>
```

> [!WARNING]
> 跨 Realm 操作时，绝不能依赖 `instanceof`。必须使用 `Array.isArray()` 或 `Object.prototype.toString.call()`。

## 6. Error.stack 分析调用链工程实践

在工程中，捕获异常并分析 `Error.stack` 是追踪执行上下文调用链的常用手段。

### 6.1 基本使用

```javascript
function a() { b(); }
function b() { c(); }
function c() {
    try {
        throw new Error("Something went wrong!");
    } catch (e) {
        console.log(e.stack);
    }
}
a();
/* 
Error: Something went wrong!
    at c (script.js:5:15)
    at b (script.js:2:16)
    at a (script.js:1:16)
    at <anonymous>:1:1
*/
```

### 6.2 异步调用栈断裂问题

标准的执行上下文调用栈无法跨越异步边界（如 `setTimeout`, `Promise`）。

```javascript
function asyncTask() {
    setTimeout(() => {
        throw new Error("Async Error"); 
        // 这里的 stack trace 只有 setTimeout 的回调，看不到是谁调用了 asyncTask
    }, 100);
}
asyncTask();
```

### 6.3 工程改造：长调用栈追踪 (Long Stack Traces)

在开发环境中，我们常常需要手动捕获调用栈以连接异步上下文。

```javascript
function runAsyncWithStack(task) {
    // 捕获当前的同步执行上下文的栈
    const captureError = new Error("Async Context Trace");
    
    setTimeout(() => {
        try {
            task();
        } catch (e) {
            // 将同步栈合并到异步错误的栈中
            e.stack += '\n--- 异步边界 ---\n' + captureError.stack;
            console.error(e.stack);
        }
    }, 100);
}

runAsyncWithStack(() => {
    throw new Error("Actual Failure");
});
```

## 7. 大量可运行代码示例综合演练

### 示例 1: 块级作用域与执行上下文

```javascript
function blockScopeDemo() {
    var x = 1;
    let y = 2;
    
    {
        var x = 100; // 覆盖外层的 x (同一个 VariableEnvironment)
        let y = 200; // 块级作用域 (新的 LexicalEnvironment)
        console.log('Inside block:', x, y); // 100, 200
    }
    
    console.log('Outside block:', x, y); // 100, 2
}
blockScopeDemo();
```

### 示例 2: 闭包与持久化的环境记录

虽然执行上下文会被销毁，但只要还有引用指向其内部的词法环境，该环境记录就不会被垃圾回收。

```javascript
function createCounter() {
    // 这里的 count 保存在 createCounter 执行上下文的 LexicalEnvironment 中
    let count = 0; 
    
    return function increment() {
        // 内部函数的 [[Environment]] 属性保留了对外部 LexicalEnvironment 的引用
        count++;
        return count;
    };
}

const counter1 = createCounter(); // createCounter 执行上下文出栈，但环境记录保留
console.log(counter1()); // 1
console.log(counter1()); // 2
```

## 总结

- **调用栈**管理执行上下文的创建与销毁。
- **VariableEnvironment** 与 **LexicalEnvironment** 的区分是理解 `var` 和 `let/const` 行为差异的根本。
- **Realm** 的存在解释了跨 iframe 环境下的类型隔离问题。
- 工程中必须注意 **TDZ**、**跨域类型检查**以及**异步环境下的栈追踪**。
