# 执行上下文与环境记录 - 实战面试题与工程陷阱

本节聚焦面试高频考点、真实工程中因对执行上下文理解不深导致的陷阱，以及手写代码题。

## 1. EnvironmentRecord 类型对比总结表

在面试中经常会被问到“JavaScript 有哪些作用域/环境？”或“var、let、with 底层有何不同？”。

| 环境记录类型 (Environment Record) | 关联结构/语法 | `this` 绑定机制 | 典型特点 |
| :--- | :--- | :--- | :--- |
| **Declarative** | `let`, `const`, `class` | 不直接管理 (由子类管理) | 纯内存键值对，查找极快。 |
| **Object** | `with` 语句, ES3时代的全局对象 | 无 | 绑定到一个真实对象，由于需要原型链查找，性能极差。 |
| **Function** | 函数调用 | 包含 `[[ThisValue]]` 状态 | 追踪 `new.target`，根据调用方式动态绑定 `this`。 |
| **Global** | 顶层脚本 (Script) | 绑定到 Global Object | 是 Object 与 Declarative 的复合体。 |
| **Module** | ES Modules (`import`/`export`) | 默认 `undefined` | 包含静态导入的不可变引用（Indirect Bindings）。 |

## 2. 真实工程陷阱分析

### 陷阱 1：递归导致的栈溢出 (Stack Overflow)
**场景**：处理海量层级的树形数据或深度计算时，直接使用递归导致 `Maximum call stack size exceeded`。
**原因**：每次函数调用推入新的 Execution Context，而 V8 引擎为每个线程分配的调用栈大小是有限的（通常在 10000 帧左右，视操作系统和内存而定）。主流浏览器（除 Safari）未实现尾调用优化（TCO）。
**规避**：将递归转换为迭代（循环），或使用蹦床函数（Trampoline）。

### 陷阱 2：`eval` 的执行上下文副作用
**场景**：在严格模式和非严格模式下滥用 `eval`。
**问题分析**：
- **非严格模式**下，`eval` 内部声明的 `var` 会“泄漏”到调用 `eval` 的词法环境中（修改当前的 VariableEnvironment）。
- **严格模式**下，`eval` 有自己独立的 Declarative Environment Record，变量不会泄漏。
**工程建议**：永远不要使用 `eval`。如果必须动态执行代码，使用 `new Function`（它总是在全局作用域执行，不会污染局部上下文）。

### 陷阱 3：跨 iframe 通信中的 `instanceof` 失效
**场景**：微前端架构或嵌套 iframe 应用中，父页面接收子页面的数据进行类型校验。
```javascript
// iframe 中传递过来的数据 msg
if (msg.payload instanceof Array) { 
    // 这里的逻辑永远不会执行！
}
```
**原因**：父页面和 iframe 拥有各自独立的 **Realm**，因此 `父页面.Array !== 子页面.Array`。
**解法**：使用 `Array.isArray()` 或 `Object.prototype.toString.call()`。

## 3. 核心手写题

### 3.1 手写：Trampoline (蹦床函数) 解决栈溢出

**题目要求**：
实现一个 `trampoline` 工具函数。要求传入一个本会栈溢出的递归函数，经过 `trampoline` 包装后，能够安全执行任意深度而不报错。

**核心思路**：
将递归转化为通过返回函数来表示下一步执行（Thunk），由蹦床函数通过 `while` 循环不断执行返回的函数，将调用栈打平，使得栈帧深度始终维持在1层。

**完整答案**：

```javascript
/**
 * 蹦床函数
 * @param {Function} fn - 需要被包装的递归函数
 * @returns {Function} - 包装后的安全函数
 */
function trampoline(fn) {
    return function (...args) {
        // 首先执行第一次，获取结果
        let result = fn.apply(this, args);
        
        // 如果结果是一个函数，说明需要继续计算，进入 while 循环
        while (typeof result === 'function') {
            // 执行返回的函数，不再是递归调用，因此调用栈没有增长
            result = result();
        }
        
        // 最终结果
        return result;
    };
}

// ======================
// 测试与应用
// ======================

// 原始递归 (n非常大时会溢出)
function sumRec(n, acc = 0) {
    if (n === 0) return acc;
    return sumRec(n - 1, acc + n);
}
// sumRec(100000); // RangeError

// 改造为返回函数的 Thunk 形式
function sumThunk(n, acc = 0) {
    if (n === 0) return acc;
    // 不直接调用，而是返回一个闭包包装的函数
    return () => sumThunk(n - 1, acc + n);
}

// 使用 trampoline 包装
const safeSum = trampoline(sumThunk);

// 现在可以安全计算超大数值了，因为 while 循环代替了调用栈的增长
console.log(safeSum(100000)); // 5000050000
```

### 3.2 手写：调用栈追踪与耗时统计装饰器

**题目要求**：
实现一个高阶函数 `traceContext`，包装任意同步或异步函数，使其在执行时能够自动打印该函数的名称、执行耗时，并能将内部可能抛出的错误的调用栈（`Error.stack`）保留原本调用方的上下文信息。

**核心思路**：
利用闭包保存调用开始时的状态，捕获一个初始 Error 实例来截断或获取当前的调用栈信息，然后通过 `try...catch`（针对同步）或 `Promise.prototype.catch`（针对异步）注入自定义的追踪信息。

**完整答案**：

```javascript
/**
 * 调用栈追踪与耗时统计装饰器
 * @param {Function} fn - 需要追踪的目标函数
 * @returns {Function} - 包装后的函数
 */
function traceContext(fn) {
    return function (...args) {
        const functionName = fn.name || 'anonymous';
        const startTime = Date.now();
        
        // 在目标函数执行前捕获当前的执行上下文栈
        const stackTraceTarget = new Error(`Context Trace for ${functionName}`);

        console.log(`[Context Trace] 🚀 Entering ${functionName}...`);

        try {
            const result = fn.apply(this, args);
            
            // 处理异步返回 (Promise)
            if (result && typeof result.then === 'function') {
                return result.then(val => {
                    const duration = Date.now() - startTime;
                    console.log(`[Context Trace] ✅ ${functionName} resolved in ${duration}ms.`);
                    return val;
                }).catch(err => {
                    const duration = Date.now() - startTime;
                    console.error(`[Context Trace] ❌ ${functionName} rejected in ${duration}ms.`);
                    // 合并异步边界处的调用栈
                    err.stack = err.stack + '\n--- async context trace ---\n' + stackTraceTarget.stack;
                    throw err;
                });
            }
            
            // 处理同步返回
            const duration = Date.now() - startTime;
            console.log(`[Context Trace] ✅ ${functionName} completed in ${duration}ms.`);
            return result;
            
        } catch (err) {
            const duration = Date.now() - startTime;
            console.error(`[Context Trace] ❌ ${functionName} failed in ${duration}ms.`);
            // 合并执行上下文栈
            err.stack = err.stack + '\n--- sync context trace ---\n' + stackTraceTarget.stack;
            throw err;
        }
    };
}

// ======================
// 测试与应用
// ======================

const riskyAsyncWork = async () => {
    return new Promise((_, reject) => {
        setTimeout(() => {
            reject(new Error("Database connection lost"));
        }, 500);
    });
};

const tracedRiskyWork = traceContext(riskyAsyncWork);

// 此时如果发生报错，抛出的错误栈中不仅包含 setTimeout 内部的回调栈，
// 还包含调用 tracedRiskyWork() 时外部环境的栈信息。
tracedRiskyWork().catch(e => {
    console.error("Caught Enhanced Error:\n", e.stack);
});
```
