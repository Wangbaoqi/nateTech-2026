# 作用域链与闭包·TDZ - 底层剖析

闭包和作用域不是魔法，它们在 ECMA-262 规范中有严谨的数据结构支撑。本节我们将深入 `LexicalEnvironment` 的内部结构、作用域链的遍历算法以及 V8 引擎是如何在堆栈中分配变量的。

## 1. 作用域链底层数据结构（`outer` 链指针）

在规范 Clause 9.1 中，每一个 Environment Record (环境记录) 都有一个内部槽位 **`[[OuterEnv]]`**。

### 1.1 链式查找模型
作用域链实际上就是一个单向链表数据结构。
- 当前作用域的 `[[OuterEnv]]` 指向外层作用域的环境记录。
- 全局环境记录的 `[[OuterEnv]]` 指向 `null`。

```javascript
const global_a = 1;
function outer() {
    const outer_b = 2;
    function inner() {
        const inner_c = 3;
        // 在此处解析 global_a
    }
}
```

**底层解析算法 `ResolveBinding(name)`：**
1. 获取当前 Running Execution Context 的 `LexicalEnvironment`（设为 `env`）。
2. 如果 `env` 为 `null`，抛出 ReferenceError (找不到变量)。
3. 调用 `env.HasBinding(name)`：
   - 如果为 `true`，返回 `env.GetBindingValue(name)`。
   - 如果为 `false`，沿着链条继续向上：设置 `env` 为 `env.[[OuterEnv]]`，跳转回步骤2。

> [!NOTE]
> 这种链式查找就是所谓的“作用域链”。由于内部函数持有对外部环境记录的引用（通过 `[[OuterEnv]]`），因此就形成了闭包的物理基础。

## 2. 变量声明三阶段机制 (var/let/const/function 对比)

在引擎处理一段代码时，标识符声明实际上经历了三个隐性阶段：
1. **创建 (Creation)**: 在环境中预留空间。
2. **初始化 (Initialization)**: 为变量分配初值（如 `undefined` 或 TDZ 绑定）。
3. **赋值 (Assignment)**: 实际执行代码中的赋值语句。

| 声明方式 | 创建阶段 | 初始化阶段 | 赋值阶段 |
| :--- | :--- | :--- | :--- |
| `var` | 进入作用域时 | 进入作用域时立即初始化为 `undefined` | 执行到 `var x = 1` 时赋值 |
| `let`/`const` | 进入作用域时 | **不进行初始化 (处于 TDZ)**，执行到声明语句时初始化 | 此时一并赋值 |
| `function` | 进入作用域时 | **完整初始化为函数对象本体** | (函数声明不可再次赋值) |

**TDZ 的规范本质**：
在规范中，如果在词法环境中为一个变量创建了绑定，但在代码执行到其词法绑定点（LexicalBinding）之前试图去 `GetBindingValue` 时，规范要求显式抛出 `ReferenceError`。这种从代码顶部到声明处的不可见状态，就是 TDZ。

## 3. LexicallyDeclaredNames vs VarDeclaredNames (Clause 8)

在规范 Clause 8 中，定义了静态语义规则以防止命名冲突。
- **LexicallyDeclaredNames**: 收集通过 `let`, `const`, `class` 声明的标识符。
- **VarDeclaredNames**: 收集通过 `var`, `function` 声明的标识符。

**Early Errors 机制**：
引擎在解析阶段（词法与语法分析，非执行阶段）会应用以下规则：
1. 同一个环境内的 `LexicallyDeclaredNames` 中如果有重复名称 -> **SyntaxError**。
2. 同一个环境内的 `LexicallyDeclaredNames` 和 `VarDeclaredNames` 中有重叠名称 -> **SyntaxError**。

```javascript
let x = 1;
var x = 2; // SyntaxError: Identifier 'x' has already been declared.
// 引擎在运行前就报错了，不会执行第一行。
```

## 4. 闭包的 `[[Environment]]` 内部槽捕获机制

在规范中，“函数是带有特定状态的对象”。
当执行到函数定义（如 function 声明、箭头函数、函数表达式）时，引擎会执行 `InstantiateFunctionObject`。

在这个过程中，引擎会将**当前正在执行的词法环境**（即创建该函数的环境）存储到新创建的函数对象的内部槽 **`[[Environment]]`** 中。

当该函数在未来被**调用**时：
1. 创建一个新的 Function Environment Record。
2. 将这个新记录的 **`[[OuterEnv]]`** 设置为该函数的 **`[[Environment]]`** 的值。

这就完美解释了为什么不论函数在哪里被调用，它的作用域链总是回到它被定义的地方（静态/词法作用域特性）。

## 5. for(let i) 每次迭代新建作用域 (Clause 14.7.4)

对于 `for (let i = 0; i < n; i++)`，为什么能解决回调共享问题？
规范 `ForLoopEvaluation` 定义了黑魔法般的操作：**PerIterationEnvironment** (每轮迭代环境)。

1. 创建一个 `loopEnv` 包含初始化的 `i = 0`。
2. 开始循环，进行条件判断。
3. 执行循环体 `stmt`。
4. **关键步骤**：如果声明包含了词法绑定（`let`），则：
   a. 克隆当前的 `loopEnv` 创建一个新的 `iterationEnv`。
   b. 读取旧 `i` 的值。
   c. 在新环境中初始化新的 `i` 并赋为旧值。
   d. 将当前的上下文词法环境切换为这个新的 `iterationEnv`。
5. 执行 `i++`。

这就是为什么 `setTimeout` 每次捕获的都是处于完全独立的 `iterationEnv` 中的 `i` 副本。

## 6. V8 Context Slot vs Stack Slot 分配策略 (引擎优化)

从 ECMAScript 规范回到实际的 V8 引擎底层。

如果我们严格按照规范，所有的环境记录都是保存在堆 (Heap) 上的对象。但这会导致极差的性能和频繁的垃圾回收。
V8 进行了一项被称为 **逃逸分析 (Escape Analysis)** 的优化。

- **Stack Slot (栈槽位)**: 默认情况下，局部变量全部分配在 CPU 寄存器或调用栈的栈帧中。访问速度极快，函数弹栈时自动销毁。
- **Context Slot (上下文槽位 - 堆内存)**: 如果 V8 发现某个局部变量被内部函数（闭包）引用了，并且该内部函数有逃逸出当前作用域的可能（如作为返回值、绑定到事件等），V8 就会将被捕获的变量从栈上“提升”到堆上的一个 `Context` 对象中。

```javascript
function v8Demo() {
    let a = 1; // 仅限当前函数使用 -> 分配在 Stack Slot
    let b = 2; // 被闭包引用 -> 提升到 Heap 上的 Context Slot
    
    return function closure() {
        console.log(b); 
    }
}
```

> [!IMPORTANT]
> 这意味着在实际工程中，**只有真正被闭包捕获的变量才会留在内存中**。未被使用的同级变量会被 V8 优化掉并在函数结束时释放，这打破了许多人“闭包会让整个外部作用域驻留内存”的传统误区。
