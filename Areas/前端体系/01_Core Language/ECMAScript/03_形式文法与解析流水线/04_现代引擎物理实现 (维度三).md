## 一、 V8 编译前端双子星：Scanner 与 Parser 流水线

在 V8 引擎架构中，源码进入编译前端需要经历 **Scanner（扫描器）** 与 **Parser（解析器）** 的精密协作：

```
[ UTF-8/UTF-16 源码缓冲区 ]
           │
           ▼
     [ V8 Scanner ]  (src/parsing/scanner.cc)
           │
           │  NextToken() (动态结合 Parser 期望切换模式)
           ▼
     [ V8 Parser ]   (src/parsing/parser.cc)
           │
           ▼
     [ AST (抽象语法树) + Scope 作用域树 ]
```

### 1. V8 Scanner 的分词状态机优化
- **单字符向前看（Lookahead）**：V8 Scanner 维护一个缓冲区指针 `c0_`，通过预读下一个 UTF-16 字符来确定当前 Token 的走向；
- **哈希查表加速标识符与关键字识别**：V8 使用完美的最小完美哈希表（Perfect Hash）识别 ECMAScript 保留字，耗时 $O(1)$，绝不进行低效的字符串逐个字符遍历；
- **动态目标符号切换**：对应规范 Clause 12 的要求，当 Parser 当前期望解析操作数时，调用 `scanner->ScanRegExp()` 手动切换进入正则词法状态。

## 二、 工业级极速编译秘诀：全量解析（Full Parsing）vs 预解析（Pre-parsing）

在现代大型 Web 应用中，单页面引入的 JavaScript 代码可能高达数兆甚至数十兆。如果浏览器在初次加载时全量编译所有函数，将会导致页面长时间白屏卡顿。  
为此，V8 发明了革命性的 **预解析（Pre-parser）双轨机制**：

| 对比维度 | 全量解析（Full Parser） | 预解析（Pre-parser） |
| :--- | :--- | :--- |
| **触发时机** | 立即执行的顶级代码、立即调用函数表达式（IIFE） | 未立即执行的普通函数声明、类方法、事件回调 |
| **是否生成 AST？** | **生成完整的 AST 树** | **跳过 AST 生成**（大幅降低内存分配开销） |
| **是否生成字节码？** | 编译并输出完整的 Ignition 字节码 | **不生成任何字节码** |
| **是否做语法校验？** | 验证全部语法与 Early Errors | **必须验证语法错误**（若有语法错误依然必须报错） |
| **是否做作用域分析？** | 构建完整的 `Scope` 树，分配物理槽位 | **只记录外层作用域变量逃逸（Escape Analysis）** |
| **性能收益** | 速度基准 1x | **速度提升 2~3 倍**，内存节省超 70% |

### 预解析的物理陷阱：二次解析（Double Parsing）
如果一个函数原本被预解析，但紧接着在 1ms 后被立刻调用，那么 V8 不得不启动 Full Parser 对其进行二次解析！  
为了让引擎识别哪些函数应该立即全量解析，业界打包工具（如 Webpack / Vite）通过在函数外加上圆括号来**强行提示 Parser 走 Full Parser 模式**：
```javascript
// 提示 V8：这是一个立即执行函数，跳过预解析，直接全量解析构建 AST
(function initApp() {
  // ...
})();
```

## 三、 V8 内部作用域树（Scope Tree）与变量物理槽位分配

当 Parser 构建 AST 的同时，V8 伴随生成一棵平行的 **作用域拓扑树（`v8::internal::Scope`）**：

### 1. V8 内部核心作用域类继承树
```
v8::internal::Scope (基类)
  ├── DeclarationScope (声明作用域：脚本 Script、模块 Module、函数 Function)
  │     └── ModuleScope (ESM 模块专属，支持活绑定导出)
  ├── BlockScope (块级作用域：处理 { let / const } 块)
  └── WithScope (处理 with 语句，将作用域回退为动态对象查询)
```

### 2. 变量逃逸分析与物理存储决策：栈槽位 vs 堆槽位
在静态作用域分析阶段，V8 会对作用域内的每一个变量执行严格的**逃逸分析（Escape Analysis）**：

#### 决策分支一：Stack Slot（栈槽位）——极速轻量
- **判定条件**：该变量仅在当前函数栈帧内使用，**没有任何内层嵌套函数引用它（无闭包引用）**；
- **物理分配**：直接分配在函数的寄存器执行栈（Virtual Register）中；函数执行完毕栈帧弹出，内存瞬间清空，开销为 0。

#### 决策分支二：Context Slot（堆上下文槽位）——持久化闭包
- **判定条件**：该变量被内部闭包函数引用（`Variable::is_used_in_outer_scope()` 为 true）；
- **物理分配**：V8 强制在堆上创建一个 `v8::internal::Context` 对象，并将该变量固定分配在 Context 对象的物理索引槽位中；
- **影响**：即使外层函数执行完毕出栈，堆上的 Context 对象依然被闭包函数的内部指针持久引用，垃圾回收器（GC）不会将其释放。

## 四、 V8 Ignition 字节码编译前端解析

在 V8 的执行流水线中，AST 紧接着被送入 **Ignition 解释器的字节码生成器（`BytecodeGenerator`）**。

### 1. 变量访问的字节码指令对决：`var` vs `let`

#### 代码段 A：`var` 的声明与加载
```javascript
function testVar() {
  var a = 10;
  return a;
}
```
对应生成的 Ignition 字节码：
```assembly
LdaSmi [10]        ; 将小整数 10 加载到累加器 (Accumulator)
Star r0            ; 将累加器的值存入局部寄存器 r0 (即变量 a 的槽位)
Ldar r0            ; 从寄存器 r0 取出值到累加器
Return             ; 返回累加器中的值
```
- **物理特征**：极简直接，没有任何安全哨兵检查。

#### 代码段 B：`let` 的 TDZ 字节码哨兵插桩
```javascript
function testLet() {
  let a = 10;
  return a;
}
```
对应生成的 Ignition 字节码：
```assembly
LdaTheHole         ; 加载 V8 内部的特殊单例对象 "TheHole" 到累加器
Star r0            ; 将 "TheHole" 预先存入寄存器 r0 (标记此时处于 TDZ)
LdaSmi [10]        ; 运行时执行到 let a = 10，加载 10
Star r0            ; 覆盖寄存器 r0，此时 TDZ 解除
Ldar r0            ; 取出变量 a
ThrowReferenceErrorIfHole [0] ; 🛡️ TDZ 核心哨兵指令！如果依然是 TheHole 则直接崩溃
Return             ; 返回
```

> 🌟 **底层机理大揭秘**：  
> **暂时性死区（TDZ）在 V8 引擎中的物理本质，就是一个名为 `TheHole`（空洞）的底层指针！**  
> 当声明一个 `let` 变量时，V8 会在寄存器/Context 槽位中写入 `TheHole`。如果在它被赋值前试图访问它，底层指令 `ThrowReferenceErrorIfHole` 发现槽位指针等于 `TheHole`，就会立刻抛出经典的 `ReferenceError: Cannot access 'a' before initialization`！

## 五、 本章引擎底层总结

1. **Scanner + Parser 是双向紧耦合系统**：通过 `InputElementDiv` / `InputElementRegExp` 动态调节扫描模式，消除除法与正则的语法歧义；
2. **预解析（Pre-parser）是前端首屏加速的核心发动机**：通过跳过 AST 生成节省海量 CPU 周期与内存，但需要防范不合理的局部函数二次解析；
3. **作用域分析决定变量物理生死**：
   - 未逃逸变量 $\rightarrow$ 栈寄存器（Stack Slot），极速销毁；
   - 逃逸闭包变量 $\rightarrow$ 堆上下文（Context Slot），常驻内存；
4. **TDZ 的物理实现是 `TheHole` 哨兵**：通过在编译期插入 `ThrowReferenceErrorIfHole` 字节码指令，以硬件级分支检查捍卫语言规范的严格性。
