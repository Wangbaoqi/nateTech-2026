> **对应标准规范**：[ECMA-262 Clause 11：ECMAScript Language: Source Code](https://tc39.es/ecma262/#sec-ecmascript-language-source-code)  
> **核心主题**：源码物理载入、Unicode 字符演进、UTF-16 编解码数学算法、规范抽象操作实现、工程兼容性痛点与工业级防御

## 一、 规范章节定义与核心原理溯源（Clause 11 深度解密）

任何 JavaScript 引擎在执行代码、构建抽象语法树（AST）乃至词法分析之前，首先面对的是**一连串原始的字节序列（Raw Bytes）**。ECMA-262 规范的 **Clause 11（ECMAScript Language: Source Code）** 为整门语言奠定了最底层的物理输入契约。

### 1. 什么是 Source Text？规范形式化定义

根据规范 [Clause 11.1](https://tc39.es/ecma262/#sec-source-text)：
```antlr
SourceCharacter :: any Unicode code point
```
- **核心契约**：ECMAScript 源码文本（Source Text）在规范定义中，被形式化抽象为**一个由合法的 Unicode 码点（Unicode Code Points）构成的有序序列**；
- **编码范围**：覆盖从 `U+0000` 到 `U+10FFFF` 的全部 Unicode 码位空间（共计 1,114,112 个可能码位）；
- **宿主环境职责**：规范明确指出，ECMAScript 引擎本身**不规定物理源文件必须如何存储在磁盘上**。将磁盘文件、网络传输的二进制字节流转换为规范所要求的 `SourceCharacter` 序列，是**宿主环境（Host Environment，如浏览器、Node.js、Deno、Bun）**的绝对职责。

### 2. 宿主环境的字节流解码流水线

现代宿主环境将外部输入转化为 `SourceCharacter` 流的标准过程如下：

```
[ 物理存储 / 网络流 ] (UTF-8 / UTF-16 / ISO-8859-1 等原始二进制字节)
         │
         ▼ 宿主探测编码 (BOM 头检测: EF BB BF / HTTP Header: charset=utf-8)
[ 宿主解码器 (Host Decoder) ]
         │
         ▼ 解码为标准的 Unicode 标量值 (Unicode Scalar Values)
[ 统一源码字符流 SourceCharacter Sequence ]
         │
         ▼ 交付引擎编译前端核心抽象操作
[ ParseText(sourceText, goalSymbol) ] (Clause 11.1.5)
```

> ![[excalidraw/ECMAScript_源码解码与字符正规化流水线.excalidraw|100%]]

1. **BOM（Byte Order Mark）自动探测**：
   - 若字节流首部存在 `0xEF, 0xBB, 0xBF`，宿主判定为 UTF-8 编码并自动剥离该标记；
   - 若存在 `0xFE, 0xFF` 或 `0xFF, 0xFE`，分别判定为 UTF-16 大端序（BE）或小端序（LE）；
2. **默认回退编码**：现代规范和 Web 标准强制要求，若无显式声明与 BOM 头，一律以 **UTF-8** 格式进行解析；
3. **解码失败降级**：若遇到非法的字节序列（如损坏的 UTF-8 截断字节），解码器会插入 Unicode 替换字符 `U+FFFD`（），这通常会导致后续词法扫描器（Scanner）抛出 `SyntaxError: Invalid or unexpected token`。

### 3. 核心形式文法推演：`ParseText(sourceText, goalSymbol)`

在规范 [Clause 11.1.5](https://tc39.es/ecma262/#sec-parsetext) 中，定义了所有编译执行的入口抽象操作：
$$\text{ParseText}(sourceText, goalSymbol)$$
- **输入参数**：
  - $sourceText$：`SourceCharacter` 构成的序列；
  - $goalSymbol$：上下文无关文法的目标符号（如 `Script`、`Module` 或表达式产生式）；
- **操作逻辑**：
  1. 将 $sourceText$ 中的每个字符按词法规则进行扫描（Lexical Analysis）；
  2. 若解析过程中发生任何违反文法或静态语义规则（Early Errors）的情况，立即返回一个或多个 `SyntaxError` 异常列表；
  3. 若完全匹配成功，返回以 $goalSymbol$ 为根节点的解析树（Parse Tree / AST）。

## 二、 ECMAScript 字符演变与 Unicode 底层编解码体系

要真正理解 JavaScript 中关于字符、长度、截断和正则表达式的一切怪异现象，必须回溯一段长达 30 年的计算机编码历史。

### 1. 历史原罪：1995 年的 UCS-2 锁死与 1996 年 Unicode 2.0 的“背刺”

- **1991 年（Unicode 1.0）**：Unicode 联盟成立之初，认为世界上所有人类语言的文字绝不会超过 65,536 个。因此最初的 Unicode 规范被设计为固定 16 位的编码方案，称为 **UCS-2（Universal Character Set 2-byte）**；
- **1995 年 5 月（JavaScript 诞生）**：Brendan Eich 仅用了 10 天创造 Mocha（JavaScript 前身）。当时 Java 和 Windows NT 均全力押注 UCS-2，JavaScript 自然全盘继承了 UCS-2 假定：**1 个字符 = 严格占用 16 位（2 字节）物理内存**；
- **1996 年 7 月（Unicode 2.0 突变）**：Unicode 联盟发现 65,536 个码位远远无法容纳中日韩统一表意文字（CJK）、历史古文字和特殊符号，宣布打破 16 位限制，将码空间扩展到 17 个平面（共 $17 \times 65536 = 1,114,112$ 个码点），并创造了 **UTF-16** 与**代理对（Surrogate Pairs）**机制；
- **历史遗留的锁死代价**：此时 JavaScript 已经商业化发布，其底层的字符串索引、`String.prototype.length`、`charAt()`、`charCodeAt()` 全都以 **16 位代码单元（Code Unit）** 为最小单位实现。为了保持向前绝对兼容，这套 16 位机制被永久固化进了 ECMAScript 标准。

### 2. 核心概念彻底澄清：码点、代码单元、代理对与字形簇

为了避免在实际开发中产生认知混乱，必须严格区分以下 4 个层级的概念：

```
层次 1：码点 (Code Point)
        Unicode 字符集中的抽象数字编号，记作 U+XXXX (范围: 0x0 ~ 0x10FFFF)
        例如：'A' 是 U+0041，'中' 是 U+4E2D，'𠮷' 是 U+20BB7，'😀' 是 U+1F600

层次 2：代码单元 (Code Unit)
        某种编码格式在物理存储时的基本二进制步长。
        在 JavaScript 内部（UTF-16），一个 Code Unit 严格为 16 位 (0x0000 ~ 0xFFFF)。
        普通字符占用 1 个 Code Unit；生僻字/Emoji 占用 2 个 Code Unit。

层次 3：代理对 (Surrogate Pair)
        为了在 16 位空间中表示大于 0xFFFF 的码点，Unicode 预留了 2048 个保留位：
        • 高位代理 (Leading/High Surrogate): 0xD800 ~ 0xDBFF (共 1024 个)
        • 低位代理 (Trailing/Low Surrogate): 0xDC00 ~ 0xDFFF (共 1024 个)
        一个高位代理拼接一个低位代理组合成一个代理对，表示辅助平面中的一个码点。

层次 4：字形簇 (Grapheme Cluster / User-Perceived Character)
        人类视觉感官上认定的“单个字符”。
        一个字形簇可能由多个 Unicode 码点组合而成（如基础字符 + 变音符，或 Emoji + 零宽连字符 ZWJ）。
```

### 3. 代理对数学公式与位运算编解码推导

规范 [Clause 11.1.1 与 11.1.2](https://tc39.es/ecma262/#sec-utf16encodepoint) 严密定义了 UTF-16 编码与解码的数学公式：

#### (1) 编码公式：从高位码点 $C$ 计算代理对 $(H, L)$
当码点 $C > \text{0xFFFF}$（即 $C \in [\text{0x10000}, \text{0x10FFFF}]$）时：
1. 首先减去基数偏移量 $\text{0x10000}$，得到一个 20 位的剩余数值 $C' = C - \text{0x10000}$；
2. 将 $C'$ 的高 10 位作为高位代理偏移量，加在 $\text{0xD800}$ 之上：
   $$H = \lfloor C' / \text{0x400} \rfloor + \text{0xD800} = (C' \gg 10) + \text{0xD800}$$
3. 将 $C'$ 的低 10 位作为低位代理偏移量，加在 $\text{0xDC00}$ 之上：
   $$L = (C' \pmod{\text{0x400}}) + \text{0xDC00} = (C' \ \& \ \text{0x3FF}) + \text{0xDC00}$$

#### (2) 解码公式：从代理对 $(H, L)$ 还原为原始码点 $C$
若已验证 $H \in [\text{0xD800}, \text{0xDBFF}]$ 且 $L \in [\text{0xDC00}, \text{0xDFFF}]$：
$$C = (H - \text{0xD800}) \times \text{0x400} + (L - \text{0xDC00}) + \text{0x10000}$$
等价于快速位运算：
$$C = ((H - \text{0xD800}) \ll 10) + (L - \text{0xDC00}) + \text{0x10000}$$

## 三、 规范定义核心抽象算法的纯 JavaScript 完整实现

为了加深对底层规范的理解，以下使用纯原生 JavaScript 严格实现 ECMA-262 Clause 11.1 中定义的全部 4 大底层抽象操作：

```javascript
/**
 * 严格按照 ECMA-262 Clause 11.1.1 实现 UTF16EncodeCodePoint(cp)
 * 将一个 Unicode 码点编码为一个包含 1 个或 2 个 UTF-16 代码单元的数组
 * @param {number} cp - Unicode 码点 (0x0 ~ 0x10FFFF)
 * @returns {number[]} UTF-16 代码单元数值序列
 */
export function UTF16EncodeCodePoint(cp) {
  // 断言：必须是合法的 Unicode 码点
  if (!Number.isInteger(cp) || cp < 0 || cp > 0x10ffff) {
    throw new RangeError(`Invalid Unicode code point: ${cp}`);
  }

  // 1. 如果码点在基本多语言平面 (BMP) 内，直接返回单代码单元
  if (cp <= 0xffff) {
    return [cp];
  }

  // 2. 码点位于辅助平面，必须编码为代理对
  const cPrime = cp - 0x10000;
  // 高 10 位
  const leadSurrogate = Math.floor(cPrime / 0x400) + 0xd800;
  // 低 10 位
  const trailSurrogate = (cPrime % 0x400) + 0xdc00;

  return [leadSurrogate, trailSurrogate];
}

/**
 * 严格按照 ECMA-262 Clause 11.1.2 实现 UTF16SurrogatePairToCodePoint(lead, trail)
 * 将高位代理与低位代理还原为一个完整码点
 * @param {number} lead - 高位代理 (0xD800 ~ 0xDBFF)
 * @param {number} trail - 低位代理 (0xDC00 ~ 0xDFFF)
 * @returns {number} 组合后的 Unicode 码点
 */
export function UTF16SurrogatePairToCodePoint(lead, trail) {
  // 规范校验：确保属于合法的代理对范围
  if (lead < 0xd800 || lead > 0xdbff || trail < 0xdc00 || trail > 0xdfff) {
    throw new RangeError(`Invalid surrogate pair: lead=${lead.toString(16)}, trail=${trail.toString(16)}`);
  }

  return (lead - 0xd800) * 0x400 + (trail - 0xdc00) + 0x10000;
}

/**
 * 严格按照 ECMA-262 Clause 11.1.3 实现 CodePointAt(string, position)
 * 从指定字符位置提取完整码点，并返回该码点占用的代码单元长度
 * @param {string} string - 输入字符串
 * @param {number} position - 代码单元索引位置
 * @returns {{ CodePoint: number, CodeUnitCount: number, IsUnpairedSurrogate: boolean }}
 */
export function CodePointAt(string, position) {
  const size = string.length;
  if (position < 0 || position >= size) {
    throw new RangeError("Position out of bounds");
  }

  const first = string.charCodeAt(position);
  let cp = first;

  // 1. 既不是高位代理也不是低位代理 -> 普通 BMP 字符
  if (first < 0xd800 || first > 0xdfff) {
    return { CodePoint: cp, CodeUnitCount: 1, IsUnpairedSurrogate: false };
  }

  // 2. 如果是低位代理，或者位于字符串末尾的高位代理 -> 孤立代理（Unpaired Surrogate）
  if (first > 0xdbff || position + 1 === size) {
    return { CodePoint: cp, CodeUnitCount: 1, IsUnpairedSurrogate: true };
  }

  const second = string.charCodeAt(position + 1);

  // 3. 如果后续字符不是合法的低位代理 -> 孤立代理
  if (second < 0xdc00 || second > 0xdfff) {
    return { CodePoint: cp, CodeUnitCount: 1, IsUnpairedSurrogate: true };
  }

  // 4. 成功匹配完整的代理对，解码出辅助平面码点
  return {
    CodePoint: UTF16SurrogatePairToCodePoint(first, second),
    CodeUnitCount: 2,
    IsUnpairedSurrogate: false,
  };
}

/**
 * 严格按照 ECMA-262 Clause 11.1.4 实现 StringToCodePoints(string)
 * 将任意 JavaScript 字符串转换为真实的 Unicode 码点序列
 * @param {string} string - 输入字符串
 * @returns {number[]} 码点数组
 */
export function StringToCodePoints(string) {
  const codePoints = [];
  const size = string.length;
  let position = 0;

  while (position < size) {
    const { CodePoint, CodeUnitCount } = CodePointAt(string, position);
    codePoints.push(CodePoint);
    position += CodeUnitCount;
  }

  return codePoints;
}
```

## 四、 字符在 ECMAScript 全生命周期中的核心应用场景

### 1. 标识符（IdentifierName）中的 Unicode 支持与规范约束

许多开发者误以为 JavaScript 变量名只能使用英文字母、数字、下划线和美元符号。事实上，ECMAScript 拥有极其广阔的 Unicode 标识符支持（[Clause 12.7](https://tc39.es/ecma262/#sec-names-and-keywords)）：

```javascript
// 完全合法的现代 JavaScript 标识符声明：
const 变量名 = "Chinese Identifier";
const π = Math.PI;
const λ = (x) => x * 2;
const Grüße = "German Greeting";
const \u0061 = 100; // 等价于 const a = 100;
const \u{61} = 200; // ES6 引入的带大括号的码点转义 (针对 a 重新赋值)
```

- **规范底层产生式**：
  ```antlr
  IdentifierStart ::
    UnicodeIDStart
    $
    _
    \ UnicodeEscapeSequence
  
  IdentifierPart ::
    UnicodeIDContinue
    $
    _
    \ UnicodeEscapeSequence
  ```
- **核心判定标准**：
  - 依赖 Unicode 标准附件第 31 号（UAX #31：Unicode Identifier and Pattern Syntax）；
  - `UnicodeIDStart`：必须具备 Unicode 属性 `ID_Start`（所有人类语言的书写字母、汉字、假名、谚文等）；
  - `UnicodeIDContinue`：具备 `ID_Continue`（在 Start 基础上允许连接符、数字符号）；
  - **关键红线**：**Emoji 绝不是合法的标识符开始或组成部分**！
    ```javascript
    const 😀 = 1; // 💥 抛出 SyntaxError: Invalid or unexpected token
    ```
    因为 Emoji 在 Unicode 属性中被归类为 `So`（Symbol, other），并不属于 `ID_Start`。

### 2. 字符串字面量中的转义语法演化三部曲

JavaScript 源码中的字符转义语法经历了三次重大技术升级：

| 转义语法形式 | 引入版本 | 支持范围 | 典型示例 | 局限性与典型痛点 |
| :--- | :--- | :--- | :--- | :--- |
| **十六进制转义 (`\xHH`)** | ES1 (1997) | `0x00 ~ 0xFF` (单字节) | `\x41` → 'A' | 只能表示 Latin-1 字符，无法表示汉字 |
| **四位 Unicode 转义 (`\uHHHH`)** | ES3 (1999) | `0x0000 ~ 0xFFFF` (16位) | `\u4E2D` → '中' | 无法直接表达大于 `0xFFFF` 的生僻字/Emoji，必须拆成代理对 `\uD842\uDFB7` |
| **大括号码点转义 (`\u{HHHHHH}`)** | ES6 (2015) | `0x0 ~ 0x10FFFF` (全空间) | `\u{20BB7}` → '𠮷'<br>`\u{1F600}` → '😀' | 彻底消除代理对心智负担，直接映射真实码点 |

### 3. 行终止符（LineTerminators）的特殊语义与 JSON 超集（Subsume JSON）

在 [Clause 11.2](https://tc39.es/ecma262/#sec-line-terminators) 中，ECMAScript 严格定义了 4 种**行终止符（LineTerminators）**：
1. `<LF>`：换行符（Line Feed，`\u000A`，`\n`）
2. `<CR>`：回车符（Carriage Return，`\u000D`，`\r`）
3. `<LS>`：行分隔符（Line Separator，`\u2028`）
4. `<PS>`：段落分隔符（Paragraph Separator，`\u2029`）

#### 历史重大 Bug：JSON 居然不是 JavaScript 的子集！
- 在 ES2019 之前，ECMAScript 规定：**字符串字面量中严禁直接包含未经转义的行终止符**；
- 然而，RFC 7159（JSON 规范）却允许字符串中直接包含未转义的 `\u2028` 和 `\u2029`！
- 这导致了一个极其荒谬且危险的工程事故：
  ```javascript
  // 后端返回合法的 JSON 字符串：'{"text":"Line 1\u2028Line 2"}'
  // 在 ES2019 之前，如果前端使用 eval 或类似方式加载此 JSON：
  eval('({"text":"Line 1\u2028Line 2"})'); 
  // 💥 抛出 SyntaxError: Invalid or unexpected token！
  ```
- **解决方案（ES2019 "Subsume JSON" 提案）**：
  规范正式修订了语法产生式，允许在单引号和双引号字符串字面量中直接出现未经转义的 `\u2028` 与 `\u2029`，自此 **JSON 终于正式成为 JavaScript 语法的严格子集**！

### 4. 正则表达式中的 Unicode 模式进化：缺省 $\rightarrow$ `/u` $\rightarrow$ `/v`

| 正则模式标志 | 引入版本 | 对字符的匹配行为 | 典型对比示例 |
| :--- | :--- | :--- | :--- |
| **缺省模式（无标志）** | ES3 | 严格按 **16 位代码单元** 逐一匹配 | `/^.$/.test("𠮷") === false`（因为被当作 2 个字符） |
| **`/u`（Unicode 模式）** | ES6 | 按 **Unicode 码点** 进行匹配；支持 `\u{...}` 转义与 `\p{...}` 属性转义 | `/^.$/u.test("𠮷") === true`；<br>`/^\p{Script=Han}+$/u.test("前端") === true` |
| **`/v`（Unicode Sets 模式）** | ES2024 | 支持**字形簇集合运算（差集 `--`、交集 `&&`）**与字符串集合匹配 | `/[^\q{👨‍👩‍👧‍👦}]/v`（可安全把复合 Emoji 作为一个不可拆分的整体处理） |

## 五、 真实工程痛点、兼容性陷阱与防御方案

### 1. 长度悖论：`str.length` 为何不能代表真实字符数？

任何现代前端项目，只要涉及用户昵称、评论输入框字数限制或文本排版，都会遭遇著名的“长度悖论”：

```javascript
// 现象 1：生僻字长度翻倍
"𠮷".length; // 2！(占用了 2 个 UTF-16 代码单元)

// 现象 2：普通 Emoji 长度翻倍
"😀".length; // 2！

// 现象 3：复合家庭 Emoji 长度失控爆炸
"👨‍👩‍👧‍👦".length; // 8！
```

#### 为什么一个家庭 Emoji 长度会是 8？
在底层，`"👨‍👩‍👧‍👦"` 根本不是一个单一码点，而是一个由 **7 个独立码点** 通过 **零宽连字符（ZWJ, Zero Width Joiner, U+200D）** 粘合而成的字符序列：
```
👨 (U+1F468, 2单元) + [ZWJ (U+200D, 1单元)] + 
👩 (U+1F469, 2单元) + [ZWJ (U+200D, 1单元)] + 
👧 (U+1F467, 2单元) + [ZWJ (U+200D, 1单元)] + 
👦 (U+1F466, 2单元)
总代码单元数 = 2 + 1 + 2 + 1 + 2 = 8 个！
```
若在前端简单使用 `if (input.value.length > 10)` 进行表单校验，用户只输入了一个 Emoji 和两个字就会提示“字数超限”！

### 2. 截断灾难：`slice` 劈开代理对导致的孤立代理项与乱码

若直接使用 `str.slice(0, 1)` 或 `str.substring()` 截取包含生僻字或 Emoji 的文本，会产生极其严重的物理截断：

```javascript
const str = "𠮷祥如意";
const broken = str.slice(0, 1); 

console.log(broken); // 输出: "" (无法显示的乱码)
console.log(broken.charCodeAt(0).toString(16)); // "d842" (这是一个孤立的高位代理！)
```

#### 引擎后果：
1. 孤立代理项（Lone Surrogate）在传输给后端数据库（如 UTF-8 编码的 MySQL `utf8mb4`）时，会被数据库判定为非法字节拒绝写入，甚至引发服务器 `Internal Server Error`；
2. 在调用 `JSON.stringify` 时（在 ES2019 之前），孤立代理项会直接输出乱码；ES2019 之后虽然修复为转义形式 `"\ud842"`，但仍无法还原原意。

### 3. 视觉完全相同但全等判断为 `false` 的幽灵 Bug：Unicode 等价性

请观察以下两行在浏览器中肉眼完全一致的文本：

```javascript
const s1 = "é"; // 形式 A
const s2 = "é"; // 形式 B

console.log(s1 === s2); // 💥 输出: false！
console.log(s1.length); // 1
console.log(s2.length); // 2
```

#### 底层原因解密：
- `s1` 是一个单一预组装字符（Precomposed Character）：码点为 `U+00E9`（LATIN SMALL LETTER E WITH ACUTE）；
- `s2` 是一个组合字符序列（Decomposed Sequence）：基础字符 `e`（`U+0065`）+ 组合钝音符 `´`（Combining Acute Accent，`U+0301`）；
- 两者在渲染层由字体排印引擎合并为完全相同的视觉形态，但在 JavaScript 的底层二进制内存中，它们拥有不同的代码单元序列，导致 `===` 判定彻底失败！

#### 解决方案：规范化（Normalization，Clause 22.1.3.13）
必须显式调用 `String.prototype.normalize()`：
```javascript
console.log(s1.normalize("NFC") === s2.normalize("NFC")); // ✅ 输出: true！
```
- **NFC（Canonical Decomposition, followed by Canonical Composition）**：优先组装为单码点，Web 文本存储的绝对行业标准；
- **NFD（Canonical Decomposition）**：全部拆分为基础字符与独立音标。

### 4. 安全攻击防范：不可见字符与特洛伊源码（Trojan Source）

在 2021 年爆出的国际顶级 CVE 漏洞 **"Trojan Source"（特洛伊源码，CVE-2021-42574）** 中，黑客正是利用了 Unicode 的方向控制字符：

```javascript
// 表面上看是一段完全正常的权限校验代码：
// 肉眼所见：
const isAdmin = false;
/* begin admins only */ if (isAdmin) {
  console.log("Welcome, Admin!");
}

// 实际物理字符（注入了 U+202E Right-to-Left Override 字符）：
// 双向文本引擎在渲染时，将后面的代码全部倒叙展示给开发者，
// 但在编译器语法分析中，实际执行逻辑与视觉呈现完全相反！
```
此外，零宽空格（Zero-Width Space `\u200B`）经常被黑客隐藏在变量名中，使两个看似同名的变量在作用域中指向不同的内存槽位，实施变量劫持。

## 六、 现代工业级高可靠字符处理工具库（生产级封装）

针对上述所有痛点，以下提供一套无外部依赖、遵循最新规范、兼顾性能的高可靠工具库：

```typescript
/**
 * 生产级字符处理工具箱 (Production-Grade Unicode Utilities)
 */
export class UnicodeUtils {
  // 单例缓存 Intl.Segmenter 实例，避免重复初始化的昂贵开销
  private static segmenter: Intl.Segmenter | null = 
    typeof Intl !== "undefined" && Intl.Segmenter 
      ? new Intl.Segmenter(undefined, { granularity: "grapheme" }) 
      : null;

  /**
   * 1. 获取真实的人类感知字符数 (Grapheme Cluster Count)
   * 准确处理一切普通字符、生僻字、复杂复合 Emoji (👨‍👩‍👧‍👦)
   */
  static getTrueLength(text: string): number {
    if (!text) return 0;
    
    // 首选现代标准的 Intl.Segmenter
    if (this.segmenter) {
      let count = 0;
      for (const _ of this.segmenter.segment(text)) {
        count++;
      }
      return count;
    }

    // 降级方案：利用 Array.from 解码为码点 (注意：复合 Emoji 仍会被拆分为多个码点)
    return Array.from(text).length;
  }

  /**
   * 2. 安全截断文本 (Safe Substring / Slice)
   * 绝对不会劈开代理对，保证输出绝对合法的字符序列
   * @param text 原始字符串
   * @param limit 限制字形簇数量
   */
  static safeSlice(text: string, limit: number): string {
    if (!text || limit <= 0) return "";

    if (this.segmenter) {
      let result = "";
      let count = 0;
      for (const { segment } of this.segmenter.segment(text)) {
        if (count >= limit) break;
        result += segment;
        count++;
      }
      return result;
    }

    // 降级方案：按码点安全切片
    return Array.from(text).slice(0, limit).join("");
  }

  /**
   * 3. 规范化安全对比 (Canonical Safe Comparison)
   * 消除预组装字符与组合音标序列的假不相等
   */
  static areEqual(str1: string, str2: string): boolean {
    if (str1 === str2) return true;
    if (!str1 || !str2) return false;
    return str1.normalize("NFC") === str2.normalize("NFC");
  }

  /**
   * 4. 源码安全检测：排查隐秘的不可见字符与双向控制字符 (Trojan Source 拦截)
   */
  static detectDangerousCharacters(sourceCode: string): { line: number; col: number; char: string; codePoint: string }[] {
    const dangerousRegex = /[\u202A-\u202E\u2066-\u2069\u200B-\u200D\uFEFF]/g;
    const issues: { line: number; col: number; char: string; codePoint: string }[] = [];
    
    const lines = sourceCode.split(/\r?\n/);
    lines.forEach((lineText, lineIdx) => {
      let match: RegExpExecArray | null;
      while ((match = dangerousRegex.exec(lineText)) !== null) {
        issues.push({
          line: lineIdx + 1,
          col: match.index + 1,
          char: match[0],
          codePoint: `U+${match[0].codePointAt(0)!.toString(16).toUpperCase().padStart(4, "0")}`,
        });
      }
    });

    return issues;
  }
}
```

## 七、 核心心智模型总结与速查表

### 1. 字符核心心智黄金法则
1. **内存存的是单元，用户看的是字形**：  
   `str.length` 统计的是 16 位 UTF-16 代码单元数；`for...of` 和 `Array.from` 遍历的是 Unicode 码点数；`Intl.Segmenter` 统计的才是人类视觉感知到的真正字形簇。
2. **永远不要用 `slice` 裸切不可控字符串**：  
   在处理用户输入、截取文本摘要时，直接用 `slice` 极易切碎代理对产生孤立代理项 `\uD800~\uDFFF`，污染数据库并引发运行时崩溃。
3. **入库与比对前必须 `normalize('NFC')`**：  
   一切来自外部的文本在执行相等性判断、全文检索或唯一主键校验之前，必须统一规范化为 NFC 形式。
