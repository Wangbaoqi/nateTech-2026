## 一、 Clause 5：文法记号约定与多重文法分流体系

### 1. 上下文无关文法（CFG）形式化定义（Clause 5.1.1）
ECMA-262 采用严格的上下文无关文法定义语言结构。产生式（Production）以非终结符（Nonterminal）开头，后跟一个或多个冒号及备选项：
$$Nonterminal : Alternative$$

- **词法文法（Lexical Grammar）**：使用 `::` 隔开，定义字符序列如何组合成词法单元（Token）；
- **句法文法（Syntactic Grammar）**：使用 `:` 隔开，定义 Token 如何组合成抽象语法树（AST）；
- **数字字符串文法（Numeric String Grammar）**：使用 `:::` 隔开，定义 `ToNumber` 转换时的合法字符串序列。

### 2. 词法扫描器的 4 大目标符号分流（Goal Symbols，Clause 5.1.2）
词法解析器（Scanner）并不是一个固定的状态机。规范明确规定，词法扫描器必须**根据语法分析器当前所处的上下文，动态切换目标符号（Goal Symbol）**：

| 目标符号（Goal Symbol） | 适用语法上下文 | 核心消歧义作用 |
| :--- | :--- | :--- |
| **`InputElementDiv`** | 当前期待**操作符**时（例如紧跟在标识符、数字字面量或 `)` 之后） | 将 `/` 字符解析为除法操作符（`DivPunctuator`），将 `/=` 解析为除后赋值 |
| **`InputElementRegExp`** | 当前期待**操作数/表达式开头**时（例如紧跟在 `=`、`(`、`,`、`return` 之后） | 将 `/` 字符作为正则表达式字面量（`RegularExpressionLiteral`）的起始界定符 |
| **`InputElementTemplateTail`** | 解析模板字符串内部变量插值表达式闭合 `}` 之后 | 识别模板字符串尾随片段或结束反引号 |
| **`InputElementHashbangOrRegExp`** | 仅用于解析**源码文件的第一行字符** | 识别类似 `#!/usr/bin/env node` 的可执行脚本头（Hashbang Comment） |

#### 形式化消歧义实例：
```javascript
// 语句 1：x 之后期待操作符 -> 使用 InputElementDiv
var x = a / b / g; // 两个连续的除法运算

// 语句 2：= 之后期待操作数 -> 使用 InputElementRegExp
var x = / a / g;   // 解析为正则表达式 literal / a /g
```
> 💡 **规范定理**：语法分析器（Parser）与词法分析器（Scanner）并非单向解耦流水线，而是**双向握手协同**：Parser 通过反馈上下文指导 Scanner 的分词模式。

## 二、 Clause 12：词法文法与自动分号插入（ASI）形式化算法

### 1. 产生式语法中的行终止符约束
在 Clause 12 中，定义了 4 类合法的行终止符（LineTerminator）：
- `<LF>` (`\u000A`)：换行符
- `<CR>` (`\u000D`)：回车符
- `<LS>` (`\u2028`)：行分隔符
- `<PS>` (`\u2029`)：段落分隔符

### 2. ASI 自动分号插入的形式化 3 大规则（Clause 12.10.1）
当代码中某处从左至右扫描时，遇到了不符合当前句法产生式的 Token（称为“离格标记” Offending Token）：

#### 规则 1（离格标记遇到换行或右花括号）：
- 只要满足以下条件之一，引擎将在该离格标记之前**虚拟插入一个分号**：
  1. 离格标记与前一个 Token 之间**至少隔了一个行终止符（LineTerminator）**；
  2. 离格标记正是 `}` 闭合花括号。

#### 规则 2（到达源码输入流末尾 EOF）：
- 当词法分析器遇到输入流末尾（End of Stream / EOF），且此时语法解析器未能推导出一个完整的语句时，将在文件末尾**虚拟插入一个分号**。

#### 规则 3（受限产生式强制插入 [no LineTerminator here]）：
- 语法产生式中明确标注了 `[no LineTerminator here]` 的节点，若其后紧随换行符，**无论后面紧跟什么 Token，引擎强制插入分号**！
- **现代规范受限产生式全集表**：
  1. `UpdateExpression : LeftHandSideExpression [no LineTerminator here] ++`
  2. `UpdateExpression : LeftHandSideExpression [no LineTerminator here] --`
  3. `ContinueStatement : continue [no LineTerminator here] Identifier;`
  4. `BreakStatement : break [no LineTerminator here] Identifier;`
  5. `ReturnStatement : return [no LineTerminator here] Expression;`
  6. `ThrowStatement : throw [no LineTerminator here] Expression;`
  7. `YieldExpression : yield [no LineTerminator here] Expression;`
  8. `ArrowFunction : ArrowParameters [no LineTerminator here] => ConciseBody`
  9. `AsyncMethod : async [no LineTerminator here] PropertyName ...`

## 三、 Clause 8：句法导向操作（Syntax-Directed Operations）与早期错误拦截

在 TC39 最新官方规范中，**Clause 8 被提升为独立的顶层核心架构**。它定义了不依赖代码执行，而直接依据语法产生式拓扑结构递归求值的静态元算法。

### 1. 早期错误检查（Early Errors，Clause 8 核心机制）
Early Errors 必须在执行任何一段代码前进行静态拦截并抛出 `SyntaxError`：

#### 检查 1：LexicallyDeclaredNames 冲突检测
- **规范定义**：若一个作用域（Script、Module、Block 或 FunctionBody）的 `LexicallyDeclaredNames` 包含重复项，或者其包含的名称同时存在于 `VarDeclaredNames` 中，**必须抛出 SyntaxError**。
- **算法形式化判定**：
  $$\text{LexicallyDeclaredNames} \cap \text{VarDeclaredNames} \neq \emptyset \implies \text{SyntaxError}$$
- **代码直观体现**：
  ```javascript
  var a = 1;
  let a = 2; // 💥 SyntaxError: Identifier 'a' has already been declared
  ```

#### 检查 2：重复参数检测（Clause 15.1.1）
- 函数形式参数列表（FormalParameters）：
  - 若处于严格模式（Strict Mode），或参数列表中包含解构模式（Destructuring）、默认值（Default Value）或 Rest 展开：
    $$\text{BoundNames of FormalParameters contains duplicates} \implies \text{SyntaxError}$$

### 2. 静态语义求值：标识符收集算法（Static Semantics）

#### 算法一：`BoundNames` 递归推导（Clause 8.1）
`BoundNames` 用于递归提取任何语法结构所产生的全部有效标识符：
- 对于单个标识符 `Identifier`：
  $$\text{BoundNames}(Identifier) = [ Identifier ]$$
- 对于对象解构 `BindingObject : { BindingPropertyList }`：
  $$\text{BoundNames}(BindingObject) = \bigcup \text{BoundNames}(BindingProperty)$$
- 对于数组解构 `BindingArray : [ BindingElementList ]`：
  $$\text{BoundNames}(BindingArray) = \bigcup \text{BoundNames}(BindingElement)$$

#### 算法二：`VarDeclaredNames` vs `LexicallyDeclaredNames`（Clause 14.1 & 14.2）
- **`VarDeclaredNames` 遍历策略**：
  - 遇到 `VariableStatement`（即 `var` 声明），提取其 `BoundNames`；
  - 穿透 `Block`、`IfStatement`、`WhileStatement`、`ForStatement`、`SwitchStatement`，继续递归向下搜集所有的 `var` 声明（**穿透块级边界，这是 `var` 穿透块作用域的数学解释**）；
  - 遇到新的 `FunctionDeclaration` 时**停止深入**（被函数边界拦截）。
- **`LexicallyDeclaredNames` 遍历策略**：
  - 仅提取当前块顶级的 `LexicalDeclaration`（`let`、`const`、`using`）和直接嵌套的 `FunctionDeclaration`、`ClassDeclaration`；
  - **绝不穿透任何子块（Sub-blocks）**。

## 四、 Clause 13~16：核心句法文法展开与解析树生成

### 1. 表达式文法（Clause 13 Expressions）与运算优先级
ECMA-262 通过产生式嵌套的深浅，形式化地锁定了运算符优先级：
```
PrimaryExpression (字面量、标识符、this、圆括号)
  └── MemberExpression (属性访问 .、[ ]、new 带参调用)
        └── CallExpression (函数调用 ( ))
              └── UpdateExpression (++、--)
                    └── UnaryExpression (typeof、void、delete、!)
                          └── BinaryExpression (*, /, +, -, <, ==, ...)
                                └── ConditionalExpression (三元运算符 ? :)
                                      └── AssignmentExpression (=, +=, ...)
                                            └── Expression (逗号运算符 ,)
```
> 产生式层级越深，结合性越紧密，优先级越高。AST 树构建严格按照此推导层级自底向上展开。

### 2. 脚本模式 vs 模块模式的文法分歧（Clause 16）

| 语言构造 | Script 模式（Clause 16.1） | Module 模式（Clause 16.2） |
| :--- | :--- | :--- |
| **严格模式** | 默认非严格模式，需显式声明 `"use strict"` | **默认全局严格模式** |
| **顶级 `await`** | 产生式中禁止直接使用 `await`（抛 SyntaxError） | **合法产生式**（顶级 await 自动包装为 Promise） |
| **`import` / `export`** | 禁止静态 import/export（抛 SyntaxError） | **合法静态模块依赖产生式** |
| **顶层 `this` 绑定** | 绑定为全局对象 `globalThis` | **绑定为 `undefined`** |
